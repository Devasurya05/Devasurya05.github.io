How I work

Four rules, each one earned on a real build.

01

Don't trust the black box.

A model that's merely accurate isn't finished. The retinal classifier ships a Grad-CAM heatmap with every prediction and holds it to a clinical bar — glaucoma attention must land on the optic disc, or the accuracy number doesn't matter. Explainability as a correctness check, not a feature.

02

Benchmark, don't guess.

ResNet18 versus Swin Transformer wasn't decided by fashion — both ran the same task and the numbers picked the winner. AutoPrompt does the same to prompts: baseline and optimized pipelines run concurrently, scored against held-out data, and the evidence decides.

03

Build for the second user on day one.

TraceFlow was multi-tenant before it had its second tenant — every query scoped by tenant ID from the first commit, because retrofitting isolation onto a single-user demo is how data leaks are born.

04

Ship the whole path.

A notebook is not a deliverable. The eye-disease model is live on Hugging Face Spaces; TraceFlow and the price engine run containerized with real frontends. If a recruiter can't click it, it isn't done.

Fire, directed

A smith doesn't fear the fire — he directs it. I work with LLMs the same way: AutoPrompt is a framework that makes a model optimize its own prompts under measurement, and this site itself was forged in a directed collaboration with Claude — spec written first, every pass critiqued against it, nothing generated left standing unexamined. Prompting well is a craft skill; the evidence is in this workshop.

The centerpiece

TraceFlow

A factory floor doesn't wait for a human to be free. TraceFlow is the answer to a specific engineering bet: root-cause analysis for manufacturing faults, running as an asynchronous, multi-tenant service from day one — not a single-user demo bolted onto multi-tenancy later.

  • FastAPI · async · Python 3.12
  • PostgreSQL 16
  • ChromaDB
  • Gemini 3.5 Flash
  • Docker
  • React + Vite
Ingestion

Factory equipment doesn't fail politely. It fails constantly, and the person who can diagnose it is rarely the person watching the dashboard when it happens. The engineering decision: never make the caller wait on the real analysis. An error comes in over HTTP POST and gets an immediate 202 Accepted with a tracking ticket — the API's job ends there. A background worker takes it from here.

POST /api/v1/incidents → 202 Accepted · ticket: queued
Investigation

A root cause isn't just this machine's history — it's this machine's history read against the technical manuals that explain what the symptoms mean. The worker pulls fault history from PostgreSQL and runs a metadata-scoped vector search over manuals in ChromaDB, scoped to the submitting tenant's ID — so one customer's equipment data never leaks into another's retrieval results.

WORKER → PostgreSQL (fault history) + ChromaDB (tenant-scoped retrieval)
Synthesis

Structured history and retrieved manual excerpts combine into one context window, sent to Gemini 3.5 Flash to synthesize a preliminary RCA report. The demo proves this generalizes across two unrelated manufacturing domains — injection molding and CNC calibration — on the same architecture, same code path.

GEMINI 3.5 FLASH → RCA report → GET /api/v1/incidents/{ticket_id}
Outcome

A factory-floor error becomes a synthesized root-cause report without a human in the loop until the answer is ready to read — and a minimal React + Vite frontend handles submission, status polling, and markdown report rendering, so the whole path from incident to answer is real, not just the backend half of it.

Explainable ML

Explainable Eye Disease Detection

The stakes

A medical model that's merely accurate isn't good enough. If it can't show its reasoning, a clinician has no way to catch it when it's confidently wrong — and a wrong diagnosis with no visible logic behind it is a liability, not a tool.

The decision

Don't commit to one architecture and hope — put a classic CNN (ResNet18) and a modern Swin Transformer through the same retinal-imagery task side by side, and require both to produce a Grad-CAM attention heatmap alongside every prediction, never just a bare label.

The mechanism

A clinical-validation layer checks whether model attention actually lines up with medical expertise — glaucoma detection should highlight the optic disc, diabetic retinopathy signals should concentrate on scattered microaneurysms. Explainability as a correctness check, not an add-on bolted on after the fact.

The outcome

The CNN reaches 91.12% validation accuracy; the Swin Transformer reaches 94.08% — the gap itself is the finding: the transformer's edge comes from reading broader retinal patterns rather than isolated local features. Deployed live, not left in a notebook.

  • PyTorch 2.0+
  • timm (pretrained architectures)
  • Grad-CAM
  • Gradio
  • Hugging Face Spaces

Trained on ~4,200 retinal images across four diagnostic categories (Kaggle's Eye Diseases Classification dataset).

91.12% Validation accuracy — ResNet18 (CNN)
CONFIDENCE — 0.9408 — SWIN-TINY

LLM systems

AutoPrompt v2.0

A prompt is an edge you grind, not a sentence you guess. AutoPrompt is an LLM prompt-optimization framework on Groq's API running Llama-3.1-8B: a Meta-LLM generates and tests candidate prompts, baseline and optimized pipelines run concurrently under semaphore-managed rate limits in an asyncio pipeline, and both are scored against held-out test data — the numbers pick the winner, not taste.

90% RUNTIME REDUCTION · +13% ACCURACY OVER BASELINE

The evaluation work was carried into a co-authored IEEE/Springer conference paper — the difference between a tool that works and a result that holds up to review.

  • Python · asyncio
  • Groq API
  • Llama-3.1-8B
  • Semaphore-managed concurrency
